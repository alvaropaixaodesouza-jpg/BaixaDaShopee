==================================================
5. FILA DE ENTREGAS
==================================================

A fila deve trabalhar conceitualmente com:

DESTINATÁRIO
   -> um ou vários PACOTES

Um destinatário pode possuir vários códigos de rastreio.

Pacotes da mesma pessoa devem ficar consecutivos.

Mover uma pessoa na ordem manual deve mover todos os pacotes dela juntos.

A fila e o teclado DEVEM usar exatamente a mesma fonte de dados e exatamente a mesma ordem.

==================================================
6. REGRA DE IDENTIDADE DO DESTINATÁRIO
==================================================

NÃO normalizar nome para decidir se duas pessoas são iguais.

A comparação deve ser literal/exata.

Exemplos:

"João das Dores"
é diferente de:
"João Das Dores"

"João das Dores"
é diferente de:
"JOÃO DAS DORES"

"João das Dores"
é diferente de:
"Joao das Dores"

Maiúsculas, minúsculas e acentos importam.

Sequence vazio ou "-" não deve causar agrupamento indevido.

Não usar fuzzy matching de nome.

==================================================
7. NOMES COMPLETAMENTE EM MAIÚSCULAS
==================================================

Destinatários cujo nome inteiro estiver em MAIÚSCULAS devem ir para um bloco final da fila.

Exemplos:

JOÃO DAS DORES -> bloco final
MARIA SILVA 2 -> bloco final
João das Dores -> normal
JOÃO Silva -> normal

A regra deve verificar letras Unicode.

Números, espaços, hífens e pontuação não impedem a identificação.

Mesmo usando ordenação A-Z, bairro ou manual, o bloco totalmente em maiúsculas continua depois dos destinatários normais.

==================================================
8. ORDENAÇÃO
==================================================

Disponibilizar:

- Manual
- Nome A-Z
- Bairro

Modo Manual:
permitir drag-and-drop do bloco inteiro do destinatário.

Persistir a ordem manual.

Filtro/ordenação por bairro deve afetar tanto a lista quanto o teclado.

==================================================
9. NORMALIZAÇÃO ESPECIAL DE BAIRROS
==================================================

ATENÇÃO:
Essa normalização vale SOMENTE para o campo bairro/filtro de bairro.

NÃO usar essa lógica em nome de destinatário.

Criar uma chave normalizada interna para bairro.

Para comparar bairros:

- trim;
- lowercase;
- remover acentos apenas para comparação;
- ignorar pontuação;
- ignorar espaços duplicados;
- permitir reconhecer variantes razoáveis.

Mapeamento especial:

Qualquer variante do bairro contendo "cabucu" deve ser agrupada em:

Cabuçu

Exemplos que devem cair no mesmo grupo:

Cabuçu
CABUÇU
cabucu
Cabuçu.
Cabuçu -
Cabuçu com espaços extras

Para Bom Jesus:

"Bom Jesus"
e
"Bom Jesus dos Pobres"

representam o MESMO grupo de bairro.

Também aceitar variações de maiúsculas, acentos, espaços e pontuação.

O grupo visual pode ser chamado:

Bom Jesus

ou:

Bom Jesus / Bom Jesus dos Pobres

mas internamente deve ser uma única categoria.

Praia do Sol:
se existir, manter como Praia do Sol.

Qualquer outro bairro:
não apagar nem forçar para Cabuçu/Bom Jesus.
Preservar como categoria própria.

IMPORTANTE:
Não procurar "Cabuçu" ou "Bom Jesus" no endereço inteiro.
Usar prioritariamente o campo de BAIRRO da planilha.
Isso evita classificar uma rua incorretamente.

==================================================
10. FLUXO COM VÁRIOS PACOTES DA MESMA PESSOA
==================================================

O teclado NÃO pode avançar de destinatário a cada código.

Exemplo:

João:
BR001
BR002
BR003

Maria:
BR004

Fluxo correto:

João / pacote 1 de 3
João / pacote 2 de 3
João / pacote 3 de 3
somente então:
Maria / pacote 1 de 1

Concluir um pacote deve avançar para o próximo pacote da mesma pessoa.

Somente após o último pacote avançar para a próxima pessoa.

Nunca misturar código de um destinatário com nome de outro.

==================================================
11. CONCLUÍDAS
==================================================

Entrega concluída deve:

- sair imediatamente da fila ativa;
- sair do teclado;
- não receber mais automação;
- permanecer registrada no histórico;
- continuar concluída mesmo se o aplicativo fechar/reiniciar.

Criar área:

Arquivo > Concluídas

NÃO renderizar a lista inteira de concluídas na Home.

Usar RecyclerView/lista virtualizada para não travar com centenas ou milhares de registros.

Cada item de Concluídas deve mostrar:

CÓDIGO DE RASTREIO
NOME DO DESTINATÁRIO
ENDEREÇO

E ao lado:

DESFAZER

Exemplo visual:

BR261008765178U
JOÃO DAS DORES
Rua X, 123 - Cabuçu                 [Desfazer]

==================================================
12. PESQUISA EM CONCLUÍDAS
==================================================

Adicionar uma lupa no topo da tela Concluídas.

Ao tocar, permitir pesquisa.

Pesquisar por:

- código BR completo;
- parte do código;
- nome;
- endereço.

O principal objetivo é permitir digitar o rastreio de uma entrega baixada por engano e encontrá-la imediatamente.

A busca deve ocorrer sem carregar milhares de Views.

==================================================
13. DESFAZER CONCLUSÃO
==================================================

Existirão DUAS formas.

FORMA 1:
Após concluir uma entrega, mostrar ação discreta:

Desfazer

por alguns segundos.

FORMA 2:
Arquivo > Concluídas
pesquisar o código
tocar em Desfazer.

Ao restaurar:

- remover estado de concluída;
- devolver à fila ativa;
- devolver à posição lógica correta;
- se a pessoa ainda possui outros pacotes ativos, reinserir no bloco dela;
- não simplesmente jogar no fim da fila.

Reimportar a rota NÃO deve reativar automaticamente entregas já concluídas.

==================================================
14. BOTÃO DESFAZER NO TECLADO
==================================================

Adicionar um botão FIXO:

DESFAZER

dentro do Teclado das baixas.

Esse botão deve existir visualmente desde o momento em que o teclado abre.

Ele NÃO pode aparecer somente depois de alguma ação.

Quando não houver uma conclusão que possa ser desfeita:

- botão continua ocupando exatamente o mesmo espaço;
- pode ficar visualmente desativado.

Quando existir uma última conclusão reversível:

Desfazer restaura a última entrega concluída pelo fluxo do teclado.

Essa operação deve atualizar:

- banco;
- fila;
- destinatário/pacote atual;
- interface do aplicativo;
- teclado.

==================================================
16. BR, RG E NOME
==================================================

BR:
insere o código completo/canônico da entrega atual.

RG:
insere somente a parte numérica usada na operação.

IMPORTANTE:
A parte numérica serve apenas para colagem.

NÃO usar RG/números como identidade interna do pacote.

Internamente o pacote deve continuar identificado pelo código canônico completo.

Nome:
usar conforme configuração.

Opções:

- usar Sequence;
- usar nome alternativo/fallback.

O fallback é um campo editável pelo usuário.

Não é um nome fixo no código.

==================================================
22. EXPIRAÇÃO DAS FOTOS TEMPORÁRIAS
==================================================

A cópia criada no MediaStore é TEMPORÁRIA.

TTL desejado:

aproximadamente 5 minutos.

Depois disso, remover a cópia temporária.

Nunca apagar o original da casa.

Nunca apagar equivocadamente o original do pacote.

Controlar as URIs que o próprio aplicativo criou.

Implementar limpeza resiliente:

- limpeza programada;
- limpeza ao reabrir o app;
- limpeza de itens expirados após reinicialização.

Pode usar WorkManager/AlarmManager/cleanup-on-launch conforme apropriado.

Android pode não garantir exatamente segundo 300; garantir expiração aproximada e limpeza eventual.

==================================================
24. RECONHECIMENTO AUTOMÁTICO DAS FOTOS
==================================================

Para cada fotografia:

PRIMEIRO:
ler QR/barcode.

SEGUNDO:
extrair código de rastreio.

TERCEIRO:
comparar com códigos canônicos da rota.

A correspondência deve ser determinística e segura.

Não atribuir usando aproximação de nome.

Se barcode não funcionar:

usar OCR como fallback.

Adicionar dependência ML Kit Text Recognition se ainda não existir.

Se houver correspondência EXATA e ÚNICA:
atribuir automaticamente ao pacote.

Se:

- código ilegível;
- código não encontrado;
- mais de uma possibilidade;
- leitura inconsistente;

NÃO ADIVINHAR.

Mover para:

Fotos sem destinatário.

==================================================
30. CASAS SALVAS
==================================================

Casas salvas são dados PERMANENTES.

Rota do dia é TEMPORÁRIA.

Ao importar uma nova rota:

para cada endereço específico:

1. gerar chave normalizada de endereço;
2. procurar casa existente;
3. se existir, reaproveitar;
4. NÃO sobrescrever dados permanentes;
5. se não existir, criar casa nova automaticamente.

O usuário não deve precisar cadastrar manualmente cada endereço.

==================================================
31. NORMALIZAÇÃO DE ENDEREÇO
==================================================

A normalização de endereço é DIFERENTE da regra de nome.

Pode:

- trim;
- normalizar espaços;
- ignorar caixa;
- tratar pontuação cuidadosamente;

para evitar duplicatas.

Mas deve ter proteção contra endereços genéricos.

Não criar uma única casa chamada apenas:

Cabuçu
Bom Jesus
Saubara
Rua sem número

se não houver informação específica suficiente.

Preservar o texto original para exibição.

==================================================

ação:

EXPORTAR CASAS

Reutilizar, quando aplicável:

- nomes de colunas;
- ordem de campos;
- endereço;
- bairro;
- cidade;
- CEP;
- nome/residentes;
- demais informações de localização disponíveis.

IMPORTANTE:

O motivo dessa exportação é facilitar edição manual dos nomes das casas no Excel.

Não misturar esta exportação com a rota ativa.

Criar nome de arquivo claro, por exemplo:

casas_salvas_2026-09-26.xlsx

ou CSV equivalente se XLSX não estiver disponível.

Preferencialmente gerar XLSX se já houver suporte seguro; caso contrário CSV UTF-8 compatível com Excel.

Eliminar criação de centenas de Views manualmente para listas grandes.

Usar RecyclerView/Lazy loading quando apropriado.

Em especial:

- Concluídas;
- Rota;
- Casas;
- Fotos sem destinatário.

Miniaturas devem ser dimensionadas.

Nunca manter dezenas de bitmaps full-size simultaneamente.

Evitar processamento pesado na UI thread.

43. FRONTEND X BACKEND
==================================================

Faça uma auditoria de todas as funções existentes.

Para cada botão/controle exibido no frontend:

verifique se existe implementação real correspondente.

Para cada função importante existente no backend:

verifique se existe forma correta de acessá-la pela interface.

Remover ou corrigir:

- botão fictício;
- botão sem listener;
- tela que só aparenta funcionar;
- função backend inacessível;
- opção duplicada;
- código morto;
- estados inconsistentes.

Não apagar funcionalidade útil apenas porque a UI ainda está ruim.

==================================================
46. REGRAS DE SEGURANÇA DA IMPLEMENTAÇÃO
==================================================
Se uma mudança depender de outra, implemente a dependência primeiro.

Não crie atalhos que possam causar mistura de destinatários.

Não use nome aproximado para atribuir pacote.

Não use somente números do rastreio como identidade.

Não sobrescreva casas existentes.

Não reative concluídas por acidente.

Não apagar dados quando ocorrer exceção.

Não fazer destructiveMigration do Room.

Não fazer merge em main.

Não modificar applicationId.

Não substituir o projeto inteiro por arquitetura nova desnecessariamente.

Evoluir a base existente.

==================================================
47. FINALIZAÇÃO
==================================================

Ao terminar:

1. Execute os testes possíveis.
2. Execute build debug.
3. Corrija todos os erros de compilação.
4. Execute novamente o build.
5. Mostre um relatório indicando:
   - arquivos alterados;
   - funções implementadas;
   - funções ainda pendentes;
   - migrações realizadas;
   - riscos encontrados;
   - testes realizados;
   - resultado do build.
6. Mostre git status.
7. Mostre git diff --stat.
8. NÃO faça merge em main.
9. NÃO apague alterações locais.
10. Não declare uma funcionalidade pronta se ela existir apenas visualmente.

A versão só deve ser considerada pronta quando frontend, backend, persistência e fluxo real estiverem conectados e testados.
